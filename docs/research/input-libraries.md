# Input capture and injection libraries: Windows + Linux X11

Research date: 2026-11-20. Scope: global (system-wide, focus-independent) mouse and keyboard **capture** and synthetic **injection** on Windows and Linux X11. Primary sources only: Microsoft Learn, X.Org specification/library docs, official project repositories, official package registries, and library source code. Wayland is noted only as a caveat and is out of scope.

"Global capture" below means receiving input events system-wide (not only events targeted at the capturing process). "Injection" means synthesizing events that are delivered to other applications.

## Underlying OS APIs

### Windows

- **Global capture hooks.** `SetWindowsHookEx` installs a hook procedure associated either with one thread or with all threads in the calling thread's desktop; `WH_MOUSE_LL` (14) and `WH_KEYBOARD_LL` (13) are **global-only** hooks that monitor low-level mouse/keyboard input ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw)). The low-level mouse callback runs on the thread that installed it, so that thread must have a message loop; it may return nonzero to prevent the event reaching the rest of the hook chain or the target window ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)).
- **Hook latency/failure mode.** A low-level hook must process within `LowLevelHooksTimeout` (max allowed value 1000 ms since Windows 10 1709); on Windows 7 and later a timed-out hook is silently removed and the application is not told ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)).
- **Journal hooks are deprecated.** `WH_JOURNALRECORD` and `WH_JOURNALPLAYBACK` are "unsupported starting in Windows 11 and will be removed in a future release"; Microsoft recommends `SendInput` instead ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw)).
- **Raw Input** (`RegisterRawInputDevices`, `WM_INPUT`, `GetRawInputData/Buffer`) is an alternative capture path; Microsoft's hook documentation suggests monitoring raw input instead of low-level hooks in most low-level-hook use cases ([Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/raw-input), [LowLevelMouseProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)).
- **Injection.** `SendInput` synthesizes keystrokes, mouse motions and button clicks; it inserts events **serially** into the input stream, and those events are not interspersed with other input events ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)).
- **UIPI and held-key state.** `SendInput` is subject to User Interface Privilege Isolation: an application can inject only into applications at an equal or lesser integrity level, and neither the return value nor `GetLastError` indicates UIPI blocking ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)). It "does not reset the keyboard's current state"; callers should check `GetAsyncKeyState` and correct as necessary ([Microsoft Learn](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winuser/nf-winuser-sendinput.md)).
- **Key identity.** `KEYBDINPUT` supports virtual-key codes and `KEYEVENTF_SCANCODE` (scan code is layout-independent, virtual key can change with layout) ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput)).

### Linux X11

- **XRecord capture.** The RECORD extension records core and extension protocol inside the X server, explicitly including "all events, including input device events that do not go to any clients"; the typical sequence is `XRecordQueryVersion` → `XRecordCreateContext` → `XRecordEnableContext` → `XRecordDisableContext` → `XRecordFreeContext`, with the functions living in `libXtst` ([X.Org Record Extension Library](https://xorg.freedesktop.org/archive/current/doc/libXtst/recordlib.html)). It distinguishes `device_events` (may not have been delivered to any client) from `delivered_events` (actually delivered to one or more clients) ([X.Org Record Extension Library](https://xorg.freedesktop.org/archive/current/doc/libXtst/recordlib.html)). The library recommends two display connections: one for control, one for reading recorded protocol ([X.Org Record Extension Library](https://xorg.freedesktop.org/archive/current/doc/libXtst/recordlib.html)).
- **Grabs are exclusive redirection, not passive capture.** `XGrabPointer` "actively grabs control of the pointer" and further pointer events are reported only to the grabbing client; it fails with `AlreadyGrabbed` if another client holds the grab, and `GrabModeSync` freezes event processing until `XAllowEvents` ([X.Org man page](https://xorg.freedesktop.org/archive/current/doc/man/man3/XGrabPointer.3.xhtml)). `XGrabKeyboard` behaves analogously, reports both `KeyPress` and `KeyRelease` regardless of event selection, generates FocusIn/FocusOut, and also fails with `AlreadyGrabbed` ([X.Org man page](https://xorg.freedesktop.org/archive/current/doc/man/man3/XGrabKeyboard.3.xhtml)).
- **XTest injection.** `XTestFakeKeyEvent`, `XTestFakeButtonEvent`, `XTestFakeMotionEvent` and `XTestFakeRelativeMotionEvent` ask the server to simulate key press/release, button press/release and pointer motion ([X.Org XTEST Extension Library](https://www.x.org/archive/X11R7.7/doc/libXtst/xtestlib.html)). The simulated event is delayed by the `delay` argument; until it is processed, no other requests from that client are processed ([X.Org XTEST Extension Library](https://www.x.org/archive/X11R7.7/doc/libXtst/xtestlib.html)). XTEST is documented as a minimal test extension, "not intended to support general journaling and playback of user actions" ([XTEST man page](https://man.archlinux.org/man/extra/libxtst/XTestFakeKeyEvent.3.en)).
- **evdev/uinput.** `evdev` is the Linux kernel's generic input interface; the Rust `evdev` crate reads streams of events from input devices and can create virtual devices through `uinput` ([crate README](https://github.com/emberian/evdev/blob/main/README.md)). It exposes raw events and compensates for `SYN_DROPPED` ring-buffer overruns in its synchronizing API ([crate README](https://github.com/emberian/evdev/blob/main/README.md)).

## Per-library detail

### rdev (Rust)

- **Claim/API.** "Simple library to listen and send events globally to keyboard and mouse on MacOS, Windows and Linux (x11)" ([README](https://github.com/Narsil/rdev/blob/main/README.md), [docs.rs](https://docs.rs/rdev/latest/rdev)). Exposes `listen(callback)`, `simulate(event_type)` and, behind the `unstable_grab` feature, `grab(callback)` which can discard events before applications see them ([docs.rs](https://docs.rs/rdev/latest/rdev)).
- **Windows capture.** `listen()` installs `WH_KEYBOARD_LL` and `WH_MOUSE_LL` via `SetWindowsHookExA(..., 0)` and pumps messages with `GetMessageA` ([common.rs](https://github.com/Narsil/rdev/blob/main/src/windows/common.rs), [listen.rs](https://github.com/Narsil/rdev/blob/main/src/windows/listen.rs)).
- **Windows injection.** `simulate()` builds `INPUT` structures and calls `SendInput` ([simulate.rs](https://github.com/Narsil/rdev/blob/main/src/windows/simulate.rs)).
- **Linux X11 capture.** `listen()` opens a display, checks for the RECORD extension, creates a context over `KeyPress`…`MotionNotify` device events for all clients, and calls `XRecordEnableContext` ([listen.rs](https://github.com/Narsil/rdev/blob/main/src/linux/x11/listen.rs)). The README states the X11 listener "will not work in Wayland or in the linux kernel virtual console" ([README](https://github.com/Narsil/rdev/blob/main/README.md)).
- **Linux X11 injection.** `simulate()` calls `XTestFakeKeyEvent`, `XTestFakeButtonEvent` and `XTestFakeMotionEvent`, then flushes/syncs the display ([simulate.rs](https://github.com/Narsil/rdev/blob/main/src/linux/x11/simulate.rs)). Wheel events are synthesized as repeated button 4/5/6/7 press-release pairs in this source ([simulate.rs](https://github.com/Narsil/rdev/blob/main/src/linux/x11/simulate.rs)).
- **Key-state fidelity.** `EventType` is described as physical/QWERTY-based, while `Event.name` reflects the OS-interpreted, layout-aware text; the README warns `name` may be `None`, empty or non-displayable, and that dead keys do not work on Linux ([README](https://github.com/Narsil/rdev/blob/main/README.md)). The optional `KeyboardState` helper implements only shift and dead keys, is layout-dependent, does not support layout switching, and does not implement Linux dead keys ([README](https://github.com/Narsil/rdev/blob/main/README.md)).
- **Privileges for interception.** The `unstable_grab` API uses `evdev` on Linux and therefore works with X11 and Wayland, but the process must run as root (not recommended) or as a member of the `input` group (or `plugdev` on some distros) ([README](https://github.com/rustdesk-org/rdev/blob/master/README.md), [docs.rs](https://docs.rs/rdev/latest/rdev)).
- **Maintenance signal.** The crates.io crate is v0.5.3, published 2023-06-26 ([crates.io API](https://crates.io/api/v1/crates/rdev)); the GitHub repository is not archived and its latest commit is dated 2026-05-12 ("Add support for F13 and above") ([GitHub API](https://api.github.com/repos/Narsil/rdev/commits?per_page=1)). A RustDesk-maintained fork has commits through 2026-10-06 ([GitHub API](https://api.github.com/repos/rustdesk-org/rdev/commits?per_page=1)) but its `Cargo.toml` is version `0.5.0-2`, still points at `Narsil/rdev` as homepage/repository, and has the `unstable_grab`/`evdev-rs` lines commented out ([Cargo.toml](https://github.com/rustdesk-org/rdev/blob/master/Cargo.toml)).

### enigo (Rust)

- **Claim/API.** "Cross platform input simulation in Rust"; the supported feature list covers Linux (X11) mouse/text, Windows mouse/text, and experimental Wayland/libei paths ([README](https://github.com/enigo-rs/enigo)). It provides `move_mouse`, `button`, `text`, `key`, `held`, etc. via an `Enigo` struct ([README](https://github.com/enigo-rs/enigo)).
- **Capture: none.** The project describes itself as input *simulation*, and neither the README nor API documentation advertises a global listener/hook API ([README](https://github.com/enigo-rs/enigo), [docs.rs](https://docs.rs/enigo)).
- **Injection on both OSes.** Windows, macOS and Linux (X11) are the default supported platforms ([README](https://github.com/enigo-rs/enigo)). Linux X11 injection uses `x11rb` by default since 0.5.0 because it is "more reliable", supports raw keycodes and removes the `xdotool` runtime dependency; `xdo` remains an opt-in feature ([CHANGES.md](https://github.com/enigo-rs/enigo/blob/main/CHANGES.md)).
- **Key-state fidelity.** 0.2.0 changed behavior so all held keys are released when `Enigo` is dropped ([CHANGES.md](https://github.com/enigo-rs/enigo/blob/main/CHANGES.md)). The unreleased changelog lists a Linux fix: "`held()` reports keys and buttons after a successful `key()`/`raw()` again" ([CHANGES.md](https://github.com/enigo-rs/enigo/blob/main/CHANGES.md)). Windows 0.3.0 changes send both virtual key and scan code so applications looking at either work, and handle the language of the current window ([CHANGES.md](https://github.com/enigo-rs/enigo/blob/main/CHANGES.md)).
- **Privileges.** "No elevated privileges are needed" on Linux; on Windows, UIPI prevents injection into higher-integrity processes (e.g. Task Manager) without elevation ([Permissions.md](https://github.com/enigo-rs/enigo/blob/main/Permissions.md)).
- **Latency/delays.** The unreleased changelog removes configurable `delay`/`set_delay`/`Settings::linux_delay` as "no longer needed" ([CHANGES.md](https://github.com/enigo-rs/enigo/blob/main/CHANGES.md)); earlier versions used sleeps (0.2.0: "No more sleeps! Simulating input is done in 1 ms instead of 40+ ms" ([CHANGES.md](https://github.com/enigo-rs/enigo/blob/main/CHANGES.md))).
- **Maintenance signal.** v0.6.1 published 2025-08-28 ([crates.io API](https://crates.io/api/v1/crates/enigo)), repository pushed 2026-11-09 with 897 commits ([GitHub API](https://api.github.com/repos/enigo-rs/enigo), [repo](https://github.com/enigo-rs/enigo)); an Unreleased section is actively accumulating changes ([CHANGES.md](https://github.com/enigo-rs/enigo/blob/main/CHANGES.md)).

### pynput (Python)

- **Claim/API.** "This library allows you to control and monitor input devices. Currently, mouse and keyboard input and monitoring are supported" ([docs](https://pynput.readthedocs.io/en/latest/)). `mouse.Controller` / `keyboard.Controller` inject; `mouse.Listener` / `keyboard.Listener` monitor ([mouse docs](https://pynput.readthedocs.io/en/latest/mouse.html), [keyboard docs](https://pynput.readthedocs.io/en/latest/keyboard.html)).
- **Backends.** `win32` is the Windows default, `xorg` is the default on other systems, `uinput` is an optional Linux keyboard-only backend requiring root ([docs](https://pynput.readthedocs.io/en/latest/index.html)). Dependencies on Linux include `evdev` and `python-xlib` ([PyPI metadata](https://pypi.org/pypi/pynput/1.8.2/json)).
- **Suppression.** `Listener(suppress=True)` prevents events reaching the rest of the system; on Windows, `win32_event_filter` plus `suppress_event()` allows selective suppression ([FAQ](https://pynput.readthedocs.io/en/latest/faq.html), [mouse docs](https://pynput.readthedocs.io/en/latest/mouse.html)). The FAQ says backends other than macOS and Windows do not support suppression of specific events ([FAQ](https://pynput.readthedocs.io/en/latest/faq.html)).
- **Key-state fidelity.** Controller modifier properties reflect only pynput's **internal** state, not the OS keyboard buffer, and cannot determine whether a key is physically pressed ([keyboard docs](https://pynput.readthedocs.io/en/latest/keyboard.html)). Listeners do not maintain state; `HotKey`/`GlobalHotKeys` exist to track modifier combinations, with `canonical()` normalizing modifier state ([keyboard docs](https://pynput.readthedocs.io/en/latest/keyboard.html)).
- **Windows caveat.** "Virtual events sent by *other* processes may not be received"; pynput dispatches its own injected events to listeners in the current process. Sending key presses propagates to the system, but the OS does not consider the buttons truly pressed: no auto-repeat for held keys, and sequences such as Shift+arrow do not work as expected ([limitations](https://pynput.readthedocs.io/en/latest/limitations.html)).
- **Latency/ordering.** Listener callbacks are invoked directly from an OS thread on Windows; long-running or blocking callbacks risk freezing input for all processes, and the docs recommend dispatching to a queue ([mouse docs](https://pynput.readthedocs.io/en/latest/mouse.html), [keyboard docs](https://pynput.readthedocs.io/en/latest/keyboard.html)).
- **Injected-event detection.** Since 1.8.0, callbacks receive an `injected` flag identifying injected input; 1.8.1 added it to events and 1.8.2 filled in the missing macOS case ([PyPI release notes](https://pypi.org/pypi/pynput/1.8.2/json)).
- **Maintenance signal.** v1.8.2 released 2026-05-12 ([PyPI API](https://pypi.org/pypi/pynput/1.8.2/json)), same-day release commit in the repo ([commit](https://github.com/moses-palmer/pynput/commit/afc64577b069a51a91474a235f0efbb0e7e0357d)), repository not archived ([GitHub API](https://api.github.com/repos/moses-palmer/pynput)).

### python-Xlib / Xlib XTest (Linux X11 only)

- **Scope.** Pure-Python X client library; its own description says it "will only work on systems that have an X server installed" and "will not work on Windows or MacOS" ([PyPI metadata](https://pypi.org/pypi/python-xlib/)).
- **Capture and injection extensions.** The project lists implemented extensions including RECORD, XTEST, XInput, XFIXES and RANDR ([PyPI description](https://pypi.org/pypi/python-xlib/)). XRecord and XTest provide the underlying capture/injection semantics described in the OS section ([X.Org Record](https://xorg.freedesktop.org/archive/current/doc/libXtst/recordlib.html), [X.Org XTest](https://www.x.org/archive/X11R7.7/doc/libXtst/xtestlib.html)).
- **Maintenance signal.** Latest release is 0.33, uploaded 2022-12-25 ([PyPI API](https://pypi.org/pypi/python-xlib/json)), and the tip commit "Update CHANGELOG, bump version to 0.33" is also dated 2022-12-25 ([GitHub API](https://api.github.com/repos/python-xlib/python-xlib/commits?per_page=1)). Its PyPI metadata still advertises Python 2.7 support ([PyPI metadata](https://pypi.org/pypi/python-xlib/)).

### Other primary-source-backed options

- **xdotool / libxdo** (Linux X11): "xdotool lets you simulate keyboard input and mouse activity... using X11's XTEST extension and other Xlib functions"; `libxdo` is the accompanying C library ([README](https://github.com/jordansissel/xdotool/blob/master/README.md)). Its Wayland section states typing, window searching and many other functions do not work correctly there ([README](https://github.com/jordansissel/xdotool/blob/master/README.md)). Repo pushed 2026-09-20 ([GitHub API](https://api.github.com/repos/jordansissel/xdotool)).
- **evdev / uinput** (Linux): reads kernel input event streams and creates virtual input devices via `uinput` ([README](https://github.com/emberian/evdev/blob/main/README.md)). `/dev/input` permissions matter: rdev's docs state evdev-based interception needs root or membership in `input`/`plugdev` ([docs.rs](https://docs.rs/rdev/latest/rdev)). Repo pushed 2026-05-28 ([GitHub API](https://api.github.com/repos/emberian/evdev)).
- **Interception** (Windows): a kernel-driver API to intercept and control input devices; driver installation requires an administrator prompt ([README](https://github.com/oblitum/Interception/blob/master/README.md)). Its README reports testing from Windows XP to Windows 10 ([README](https://github.com/oblitum/Interception/blob/master/README.md)). Repo pushed 2021-08-09 ([GitHub API](https://api.github.com/repos/oblitum/Interception)).
- **Windows.UI.Input.Preview.Injection** (UWP/packaged apps): Microsoft documents input injection that can target apps outside the caller's client area, even elevated ones, but requires the `inputInjectionBrokered` restricted capability in the app manifest ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/design/input/input-injection)).

## Known limitations

- **Privileges.** Windows `SendInput` cannot inject into a higher-integrity process due to UIPI ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)); enigo documents that elevation is needed for such targets ([Permissions.md](https://github.com/enigo-rs/enigo/blob/main/Permissions.md)). X11 itself needs no elevation for enigo ([Permissions.md](https://github.com/enigo-rs/enigo/blob/main/Permissions.md)), but pynput's Linux `uinput` backend requires root ([limitations](https://pynput.readthedocs.io/en/latest/limitations.html)) and rdev's evdev `grab` needs root or `input`/`plugdev` membership ([README](https://github.com/rustdesk-org/rdev/blob/master/README.md)). Interception driver installation requires admin rights ([README](https://github.com/oblitum/Interception/blob/master/README.md)).
- **Held-key / key-state fidelity.** Windows `SendInput` does not reset keyboard state and may be interfered with by already-pressed keys ([Microsoft Docs source](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winuser/nf-winuser-sendinput.md)). pynput's Windows injected key presses are not "truly pressed": no auto-repeat and broken Shift+arrow sequences ([limitations](https://pynput.readthedocs.io/en/latest/limitations.html)); its controller modifiers are internal-only state ([keyboard docs](https://pynput.readthedocs.io/en/latest/keyboard.html)). rdev's `KeyboardState` is layout-dependent and implements only Shift/dead keys ([README](https://github.com/Narsil/rdev/blob/main/README.md)). enigo releases held keys on drop and has had specific fixes for `held()` and modifier handling ([CHANGES.md](https://github.com/enigo-rs/enigo/blob/main/CHANGES.md)).
- **Latency and ordering.** Low-level Windows hooks have a hard timeout and can be silently removed ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)); `SendInput` events are inserted serially and not interspersed with other input ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)); XTest delays block subsequent requests from the same client ([X.Org](https://www.x.org/archive/X11R7.7/doc/libXtst/xtestlib.html)); pynput warns that blocking callback work on Windows OS threads can freeze input globally ([docs](https://pynput.readthedocs.io/en/latest/mouse.html)). rdev's example inserts a 20 ms sleep between simulated events "to let the OS catchup (at least MacOS)" ([README](https://github.com/Narsil/rdev/blob/main/README.md)).
- **Wayland (note only, out of scope).** rdev's `listen` uses X11 APIs and will not work on Wayland, whereas its evdev-based `grab` works with both X11 and Wayland ([README](https://github.com/rustdesk-org/rdev/blob/master/README.md)). pynput says Xwayland gives "limited functionality" and only events from apps running under the emulator ([limitations](https://pynput.readthedocs.io/en/latest/limitations.html)). enigo's Wayland/libei/xdg-desktop backends are experimental behind feature flags with documented known issues ([README](https://github.com/enigo-rs/enigo), [KNOWN_ISSUES.md](https://github.com/enigo-rs/enigo/blob/main/KNOWN_ISSUES.md)). xdotool states many functions do not work correctly on Wayland ([README](https://github.com/jordansissel/xdotool/blob/master/README.md)).

## Key facts for decision-makers

- No single one of the named cross-platform libraries both captures globally and injects on both OSes while also being freshly released to its package registry: rdev is the only named one with both capabilities on both OSes, but its crates.io release is 0.5.3 from 2023-06-26 ([crates.io API](https://crates.io/api/v1/crates/rdev)).
- rdev's source maps directly to the OS primitives: `WH_KEYBOARD_LL`/`WH_MOUSE_LL` + `SendInput` on Windows, XRecord + XTest on Linux X11 ([windows/common.rs](https://github.com/Narsil/rdev/blob/main/src/windows/common.rs), [windows/simulate.rs](https://github.com/Narsil/rdev/blob/main/src/windows/simulate.rs), [linux/x11/listen.rs](https://github.com/Narsil/rdev/blob/main/src/linux/x11/listen.rs), [linux/x11/simulate.rs](https://github.com/Narsil/rdev/blob/main/src/linux/x11/simulate.rs)).
- enigo is injection-only; it has no documented global capture/listener API ([README](https://github.com/enigo-rs/enigo)). It is the most recently released of the Rust candidates (0.6.1, 2025-08-28) with a repository pushed 2026-11-09 ([crates.io API](https://crates.io/api/v1/crates/enigo), [GitHub API](https://api.github.com/repos/enigo-rs/enigo)).
- pynput has both global listeners and controllers on Windows and X11, and is actively released (1.8.2, 2026-05-12) ([docs](https://pynput.readthedocs.io/en/latest/), [PyPI](https://pypi.org/pypi/pynput/1.8.2/json)); its own docs state that Windows-injected key presses are not treated as truly pressed by the OS ([limitations](https://pynput.readthedocs.io/en/latest/limitations.html)).
- python-Xlib exposes the X11 RECORD and XTEST extensions needed for capture and injection, but is X11-only and its last release/commit was 2022-12-25 ([PyPI](https://pypi.org/pypi/python-xlib/), [PyPI API](https://pypi.org/pypi/python-xlib/json), [commit](https://api.github.com/repos/python-xlib/python-xlib/commits?per_page=1)).
- Windows low-level global hooks require the installing thread to run a message loop and can be silently removed on timeout ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)); XRecord can observe device events even when no client receives them ([X.Org](https://xorg.freedesktop.org/archive/current/doc/libXtst/recordlib.html)).
- XGrabPointer/XGrabKeyboard are exclusive grabs that redirect and can freeze input, and fail with `AlreadyGrabbed` if another client holds the grab; they are not passive observation APIs ([XGrabPointer](https://xorg.freedesktop.org/archive/current/doc/man/man3/XGrabPointer.3.xhtml), [XGrabKeyboard](https://xorg.freedesktop.org/archive/current/doc/man/man3/XGrabKeyboard.3.xhtml)).
- Kernel-level interception is possible but platform-specific and privileged: Interception needs admin-installed drivers and has not been pushed since 2021-08-09, while evdev/uinput on Linux needs `/dev/input` access ([Interception README](https://github.com/oblitum/Interception/blob/master/README.md), [GitHub API](https://api.github.com/repos/oblitum/Interception), [rdev docs](https://docs.rs/rdev/latest/rdev)).
